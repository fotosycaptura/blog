Copyparty: montando una nube personal ligera con Docker y Nginx Proxy Manager

  • 2026, sáb 24 octubre
  • Laboratorio
  • @fotosycaptura
  • #laboratorio, #programacion, #software, #config, #contenedor

Hace algún tiempo comencé a utilizar File Browser para administrar y compartir archivos desde mi propia infraestructura. La idea era bastante sencilla: disponer de un espacio accesible mediante un navegador, con usuarios, carpetas y permisos, sin depender de servicios externos de almacenamiento. Sin embargo... Todo cambió cuando dejó de tener soporte... Y eso, conlleva riesgos de ciberseguridad... Acompáñame a revisar con qué lo reemplacé...

Al buscar alternativas para reemplazar la instalación que utilizaba, terminé encontrándome con Copyparty, un servidor de archivos escrito principalmente en Python que destaca por su ligereza y por la cantidad de funcionalidades que ofrece.

En este artículo explicaré qué es Copyparty, sus principales características y cómo se puede instalar por ejemplo en una Raspberry Pi utilizando Docker Compose. También explicaré cómo publicarlo mediante Nginx Proxy Manager, configurar usuarios con permisos diferentes y resolver algunos inconvenientes que podrían llegar a aparecer durante la instalación.

¿Qué es Copyparty?

Copyparty es, básicamente un servidor de archivos que permite compartir, administrar, subir y descargar archivos mediante una interfaz web.

A diferencia de plataformas más complejas como Nextcloud, Copyparty no pretende ser una suite completa de colaboración, calendario o productividad. Su propósito principal es ofrecer un sistema de intercambio y administración de archivos, con una instalación relativamente sencilla y un consumo de recursos casi despreciable diría yo.

Entre sus características, destacan:

  • Interfaz web para navegar, subir y descargar archivos.
  • Cuentas de usuario con permisos diferenciados.
  • Volúmenes virtuales que permiten publicar distintas carpetas.
  • Subidas de archivos mediante el navegador.
  • Posibilidad de habilitar protocolos adicionales, según la configuración y las dependencias instaladas.
  • Compatibilidad con Linux y despliegues mediante contenedores.

Una característica especialmente interesante es su sistema de volúmenes virtuales: se puede presentar carpetas ubicadas en diferentes lugares del sistema como si pertenecieran a un mismo servidor de archivos, sin necesidad de moverlas físicamente.

¿Por qué elegir Copyparty?

Mi objetivo era mantener un servicio pequeño casero para almacenar y compartir archivos, principalmente documentos, fotografías y otros materiales personales. Antes usaba filebrowser y si bien, podría seguir utilizándolo mediante acceso VPN, tener aplicaciones legacy puede conllevar un riesgo así que mejor, usar otra alternativa...

No necesitaba una plataforma demasiado compleja. La solución debía funcionar en una Raspberry, y debería de permitir varios usuarios y ofrecer acceso remoto mediante HTTPS.

Entre otras opciones, evalué SFTPGo, que incorpora funcionalidades interesantes y soporte para diferentes protocolos de transferencia. Sin embargo, para este caso decidí probar Copyparty por su enfoque ligero y por la flexibilidad de su configuración.

Si estás interesado en ello, seguramente la infraestructura que utilizarás podría ser como la siguiente:

  • Raspberry Pi 4 con Debian.
  • Docker y Docker Compose.
  • Nginx Proxy Manager para administrar HTTPS.
  • Un dominio propio.
  • Carpetas locales y/o almacenamiento adicional.
  • Una red Docker compartida entre el proxy y Copyparty.

Preparando la estructura de directorios

Primero deberás generar un directorio de trabajo:

mkdir -p ~/mi-usuario-u-otra-ruta/copyparty
cd ~/mi-usuario-u-otra-ruta/copyparty

Dentro de él convendrá preparar algunas carpetas que serán necesarias:

mkdir -p config state files/invitado/subidas

La estructura inicial será algo como esto:

copyparty/
├── docker-compose.yml
├── config/
│   └── copyparty.conf
├── state/
└── files/
    └── invitado/
        └── subidas/

Cada directorio tiene una finalidad: - config: configuración de Copyparty. - state: información persistente de la aplicación, incluidas las sesiones. - files: archivos administrados desde la interfaz web.

Como medida de seguridad, será importante mantener separados los archivos personales y los datos internos de la aplicación.

Crear la configuración de Docker Compose

Y llegado a este punto, se usará una imagen de Copyparty y se conectará a una red Docker compartida con Nginx Proxy Manager.

Para ello, toca generar el archivo docker-compose.yml:

name: copyparty

services:
  copyparty:
    image: copyparty/min:latest
    container_name: copyparty

    user: "1000:1000"

    environment:
      TZ: America/Santiago
      PYTHONUNBUFFERED: "1"
      XDG_CONFIG_HOME: /state

    volumes:
      - ./config:/cfg:ro
      - ./state:/state:rw
      - ./files:/w:rw

    networks:
      proxy-interno:
        ipv4_address: 172.18.0.3

    mem_limit: 256m

    security_opt:
      - no-new-privileges:true

    restart: unless-stopped

networks:
  proxy-interno:
    external: true

En este ejemplo, proxy-interno es una red Docker que ya existe y que también utiliza Nginx Proxy Manager.

Antes de asignar una IP fija deberás comprobar que la red tenga una subred compatible y que la dirección elegida esté disponible:

docker network inspect proxy-interno

La IP 172.18.0.3 es únicamente la dirección utilizada en la instalación. No necesariamente será válida en otras redes, y en tu caso, puede que sea otra...

También deberás verificar que el usuario 1000:1000 tenga acceso a los directorios montados. Si los permisos no son correctos, Copyparty podría iniciar, pero no conseguir escribir sus archivos de estado o permitir las subidas.

Así que, para comprobar el UID del usuario, puedes usar el comando:

id

Si corresponde al UID 1000, normalmente podrás preparar las carpetas locales de esta forma:

sudo chown -R 1000:1000 config state files

Este comando está pensado para los directorios recién creados del proyecto, no para carpetas personales existentes que puedan contener archivos de otros usuarios.

¿Por qué se utiliza XDG_CONFIG_HOME?

Durante las primeras pruebas observé advertencias relacionadas con directorios de configuración de solo lectura.

Al establecer:

XDG_CONFIG_HOME: /state

y montar ese directorio con permisos de escritura, Copyparty puede almacenar su información persistente sin depender del sistema de archivos interno del contenedor.

Configurar usuarios y carpetas

Una de las cosas que más me llamó la atención fue su sistema de cuentas y volúmenes.

Supongamos un caso en el que necesitas dos usuarios:

  • Admin, tu usuario para administrar tus archivos y carpetas.
  • Invitados, para acceder a una carpeta compartida, con permisos de escritura limitados a un directorio específico.

Para ello, deberás de generar el archivo config/copyparty.conf, algo como esto:

[global]
  p: 3923
  xff-src: 172.18.0.2/32
  rproxy: 1

[accounts]
  admin: CAMBIAR_CLAVE_ADMIN
  invitado: CAMBIAR_CLAVE_INVITADO

[/]
  /w
  accs:
    rwmda: admin

[/invitado]
  /w/invitado
  accs:
    r: invitado
    rwmda: admin

[/subidas]
  /w/subidas
  accs:
    rw: invitado
    rwmda: admin

Las contraseñas son valores de ejemplo y deben reemplazarse por credenciales seguras. En este punto, recomendaría proteger el archivo de configuración porque contiene información sensible.

La opción xff-src indica qué dirección del proxy inverso es de confianza. En este caso corresponde a la IP interna de Nginx Proxy Manager en la red compartida. Esto es algo que deberás de verificar en tu instalación, dado que puede variar...

Comprendiendo los permisos

Copyparty permite establecer diferentes permisos sobre cada volumen.

Los principales son:

Permiso Función
r Leer y descargar
w Subir archivos y crear directorios
m Mover o renombrar
d Eliminar
a Administrar el volumen


Por ejemplo:

[/invitado]
  /w/invitado
  accs:
    r: invitado
    rwmda: admin

Esto permite que invitado lea los archivos de su directorio, pero que no pueda modificarlos.

Sin embargo, si necesitas que pueda subir archivos, puedes usar una carpeta específica para ello.

Con algo por ejemplo:

[/subidas]
  /w/subidas
  accs:
    rw: invitados
    rwmda: admin

De esta manera, el usuario invitado puede subir archivos y crear subdirectorios dentro de subidas, mientras que las demás carpetas permanecen de solo lectura.

El usuario administrador conserva todos los permisos.

Esta configuración resulta útil cuando se desea compartir documentos y, al mismo tiempo, disponer de un espacio donde otras personas puedan entregar archivos sin modificar el resto del contenido.

Iniciar Copyparty

Con los archivos preparados, lo que queda es iniciar el contenedor:

docker compose up -d

Para comprobar su estado:

docker compose ps

Y revisar los registros:

docker logs --tail 60 copyparty

En los registros deberías de encontrar mensajes indicando que Copyparty está escuchando en el puerto 3923 y que sus procesos han iniciado correctamente.

También mostrará los volúmenes configurados y sus permisos.

Durante las pruebas puedes agregar al docker-compose temporalmente un puerto para revisar la configuración, por ejemplo mediante:

ports:
  - "8080:3923"

De esta manera, te permitirá acceder al servicio utilizando la dirección IP de la Raspberry y el puerto 8080.

Solo recuerda que si vas a publicar Copyparty exclusivamente mediante Nginx Proxy Manager, no se necesita mantener ese puerto expuesto. En la configuración final deberías de utilizar únicamente la red interna de Docker.

Publicar Copyparty mediante Nginx Proxy Manager

Como en este post utilizaré Nginx Proxy Manager para publicar otros servicios, decidí aprovechar la misma infraestructura.

La arquitectura quedó aproximadamente así:

En la interfaz de Nginx Proxy Manager puedes crear un Proxy Host con los siguientes parámetros:

Parámetro Valor
Domain Names nube.ejemplo.cl
Scheme http
Forward Hostname / IP IP interna de Copyparty
Forward Port 3923
Websockets Support Activado
SSL Certificado válido
Force SSL Activado


Aunque los visitantes se conectan mediante HTTPS, la comunicación entre Nginx Proxy Manager y Copyparty puede realizarse mediante HTTP dentro de la red privada de Docker.

Primer inconveniente que puedes encontrar: error CORS

Al intentar iniciar sesión mediante el dominio público, Copyparty puede rechazar algunas solicitudes con un mensaje relacionado con CORS.

Si en los registros te aparece algo parecido a:

cors-reject POST because request-header Origin
does not match request-protocol 'http://'

Entonces tienes un problema... Pero tranquilo... Lo que ocurre es que el navegador accede mediante HTTPS, pero Copyparty interpretaba que la solicitud original había llegado mediante HTTP.

El problema estaba relacionado con el tratamiento de las cabeceras del proxy inverso y con la dirección desde la cual Copyparty recibe las conexiones.

Para solucionarlo, necesitarás revisar la configuración del proxy, la red compartida y las opciones xff-src y rproxy de Copyparty, seguramente las IPs serán diferentes que las del ejemplo, así que revisa con paciencia y cuidado...

Podrías llegar a desactivar las comprobaciones CORS para resolver este tipo de errores, pero no lo recomiendo. Lo mejor es corregir la configuración del proxy y asegurarse de que Copyparty identifique correctamente el protocolo y el origen de las solicitudes.

Segundo inconveniente que podrías obtener: 502 Bad Gateway

Después de modificar el destino de Nginx Proxy Manager para utilizar el nombre del contenedor, podrías llegar a tener un:

502 Bad Gateway
openresty

Curiosamente, Copyparty parece funcionar sin inconvenientes, pero al ingresar recibes ese error... ¿Entonces?

Si miras los logs, los registros podrían llegar a mostrar que se esta escuchando en:

http://172.18.0.3:3923/

Puedes comprobar la comunicación entre ambos contenedores con:

docker exec nginxproxymanager getent hosts copyparty

Deberías obtener algo como:

172.18.0.3 copyparty

Después si pruebas:

docker exec nginxproxymanager \
  curl -I http://copyparty:3923/

Y obtienes:

HTTP/1.1 200 OK

Esto te demuestra que Nginx Proxy Manager se comunica con Copyparty.

Entonces, ¿por qué el error 502?

Seguramente, es muy probable que el problema sea la resolución DNS de Nginx

Al revisar los registros de Nginx Proxy Manager, en mis pruebas encontré:

copyparty could not be resolved
(3: Host not found)

El contenedor utilizaba correctamente el DNS interno de Docker:

nameserver 127.0.0.11

Pero la configuración efectiva de Nginx tenía definidos servidores DNS externos, que no conocen los nombres de los contenedores Docker.

Por eso, aunque getent y curl resolvían correctamente el nombre copyparty, Nginx no conseguía hacerlo al procesar las solicitudes.

Así que, dada esa situación, en lugar de modificar la configuración global de Nginx Proxy Manager, decidí en la prueba, utilizar directamente la IP interna de Copyparty, con ese cambio, el servicio comenzó a funcionar correctamente.

Para evitar que la dirección cambiara al recrear el contenedor, puedes agregar una IP estática a su configuración de Docker Compose:

networks:
  proxy-interno:
    ipv4_address: 172.18.0.3

Esta solución requiere que la red Docker tenga una subred compatible y que la dirección esté disponible.

Otra alternativa habría sido configurar Nginx para resolver los nombres mediante el DNS interno de Docker, pero eso escapa al propósito de este artículo...

Montar carpetas externas sin copiar los archivos

Una vez que Copyparty se encuentra funcionando, puedes querer agregar una carpeta por ejemplo de fotografías que quizás ya tengas almacenada en otro directorio, o en otro disco.

Copyparty permite hacerlo sin copiar los archivos, aprovechando los montajes de Docker.

Por ejemplo, supongamos que nuestras fotografías están en una unidad externa, digamos, algo del tipo:

/media/devmon/Fotos/algo

Puedes agregar un nuevo volumen al docker-compose.yml:

volumes:
  - ./config:/cfg:ro
  - ./state:/state:rw
  - ./files:/w:rw
  - /media/devmon/algo:/fotos:ro

El parámetro :ro hace que el montaje sea de solo lectura.

Esto resulta muy conveniente para evitar modificaciones o borrados accidentales de tus fotografías personales...

Luego, en el archivo de configuración de copyparty, agregas un volumen virtual:

[/fotos]
  /fotos
  accs:
    r: admin

De esta manera, únicamente el usuario administrador podrá acceder a las fotografías.

El usuario invitado no tendrá permisos sobre ese volumen.

Conclusiones

Después de varias pruebas, Copyparty terminó siendo una alternativa interesante para mantener un pequeño servidor de archivos.

Su principal atractivo es que permite disponer de una interfaz web para administrar archivos sin instalar una plataforma demasiado compleja. Y si usas Gnome por ejemplo, puedes usar Nautilus mediante protocolo DAV para conectarse y trabajar de manera gráfica...

La posibilidad de crear volúmenes virtuales, asignar permisos por usuario y montar carpetas existentes resulta muy útil para tener una estructura organizada de almacenamiento.

En este caso de ejemplo, la instalación también sirvió para recordar algunas particularidades de Docker y Nginx Proxy Manager, especialmente la diferencia entre la resolución DNS del contenedor y la que utiliza internamente Nginx.

Finalmente, con esto se puede conseguir una instalación con acceso HTTPS, cuentas independientes, permisos por carpeta y almacenamiento compartido, funcionando en una Raspberry Pi.

Este artículo, no pretende que reemplaces todos los servicios de una nube comercial ni convertirse en una plataforma de colaboración completa, pero para compartir documentos, recibir archivos y consultar fotografías u otros documentos privados desde cualquier lugar, sin que mande telemetría a externos, cumple bastante bien...
